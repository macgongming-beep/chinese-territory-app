# 기존 호수는 제외하고 같은 건물의 중복 세대를 막는다

- 상태: **운영 적용 완료**
- 결정일: 2026-09-06
- 관련 기능: 단일 세대 추가, 호수 일괄 추가, 세대 번호 수정, 자료 가져오기

## 배경

같은 건물에 `203호`와 `203`이 별도 세대로 등록되면 방문 기록과 상태가 둘로 갈라진다.
운영의 `영일로 9`에도 이 중복이 실제로 한 건 남아 있었다. 반대로 단순 UNIQUE 오류를
사용자에게 그대로 노출하면 전수 조사 뒤 1층부터 5층까지 일괄 등록할 때, 이미 있던
`301호`와 `403호` 때문에 나머지 새 호수까지 전부 추가되지 않는 문제가 생긴다.

## 결정

1. 같은 건물에서는 정규화한 세대 번호가 같은 행을 하나만 허용한다.
2. `101`, `101호`, `101 호`, `0101`은 같은 번호로 본다.
3. `B02`, `b02호`도 같은 번호로 본다.
4. 글자 이름은 공백만 무시한다. 화면에는 사용자가 입력한 원래 표기를 유지한다.
5. 단일·일괄 추가는 서버 트랜잭션 RPC를 공통으로 사용한다.
6. 이미 있는 호수는 오류가 아니라 제외하고, 없는 호수는 모두 추가한다.
7. 결과는 `추가 N개 · 기존 N개 제외`처럼 한 번만 알린다.
8. 건물 단위 advisory lock과 UNIQUE 인덱스를 함께 사용해 동시 요청도 중복을 만들지 못하게 한다.

## 이유

- 일괄 추가의 목적은 건물을 전수 조사한 결과를 빠르게 채우는 것이다. 일부가 이미 있다는
  이유로 전체를 실패시키면 사용자가 기존 번호를 하나씩 찾아 빼야 한다.
- 클라이언트의 기존 목록은 다른 사용자의 직전 추가를 모를 수 있으므로 서버가 최신 자료로
  다시 판정해야 한다.
- UNIQUE만 두면 오류는 막지만 정상적인 부분 성공 UX를 만들 수 없고, 클라이언트 확인만 두면
  동시 요청과 앱 밖 쓰기를 막을 수 없다. 두 층이 모두 필요하다.

## 지켜야 할 계약

- `301호`, `403호`만 있는 건물에 `101~505`를 일괄 추가하면 나머지 23개는 추가된다.
- 기존 두 호수는 수정하거나 초기화하지 않는다. 상태·메모·방문 기록도 그대로다.
- 입력 목록 안의 `201`, `201호`도 하나만 추가한다.
- 두 사용자가 동시에 같은 번호를 추가해도 한 행만 생긴다.
- 양쪽 중복 행에 실제 상태나 연결 기록이 있으면 자동 삭제하지 않고 마이그레이션을 멈춘다.
- 번호 수정이 기존 번호와 충돌하면 저장하지 않고 사용자가 원래 값을 계속 볼 수 있어야 한다.
- 식당·정기방문·CSV처럼 세대를 만드는 다른 경로도 DB 제약을 우회할 수 없다.

## 구현과 검증

- 서버: `supabase/migrations/20260906_1440_unique_unit_number.sql`
- 클라이언트 저장: `src/hooks/storeMutations/buildings.ts`
- 미리보기 판정: `src/utils/bulkUnits.ts`
- 계약 시험: `src/utils/bulkUnits.test.ts`

운영의 표기 중복 1건은 `203호` 행에 `대상외` 방문 기록이 있고 `203` 행은 상태·메모·연결
자료가 전혀 없었다. 마이그레이션은 기록이 있는 행을 보존하고 빈 행만 제거한 뒤 UNIQUE를
만든다. 양쪽에 의미 있는 자료가 있는 다른 중복이 발견되면 자동 처리하지 않는다.

## 운영 상태

2026-09-06 최신 백업 뒤 운영 DB에 적용했다. 세대는 2,805개에서 2,804개가 됐고,
`영일로 9`에는 방문 기록이 연결된 `203호`만 남았다. 방문 기록 `634`의 `대상외` 결과와
방문자 `张雄장웅`을 대조했으며, 정규화 중복 0건과 UNIQUE 인덱스 생성을 확인했다.
