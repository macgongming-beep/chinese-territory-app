# 순수 호수는 `호` 없이 저장하고 자유 이름은 보존한다

- 상태: **운영 적용 완료**
- 결정일: 2026-09-06
- 관련 기능: 세대 추가·수정, 호수 일괄 추가, 정기방문 연결, CSV·백업 복원

## 배경

세대 번호가 `101`과 `101호`로 섞여 있으면 목록 표기가 어수선하고, 화면에서 다시 `호`를
붙이는 코드 때문에 `101호호`가 보이기도 했다. 운영 세대 2,804개 중 순수 호수 뒤에 `호`가
붙은 것은 375개였다. 반면 `101호 한국인`, `A동 102호`, `120호 천미가 마라탕`처럼 `호`가
주소·설명·상호의 일부인 세대도 60개 있어 일괄적인 접미사 제거는 자료를 훼손한다.

## 결정

1. 전체 값이 `숫자 + 호` 또는 `B/b + 숫자 + 호`인 경우에만 끝의 `호`를 제거한다.
2. `101호`는 `101`, `B03호`는 `B03`이 된다.
3. 앞자리 0, 영문 대소문자와 그 밖의 글자는 사용자가 적은 그대로 보존한다.
4. `A동 102호`, `810동1505호`, `101호 한국인`, 식당명 같은 자유 이름은 변경하지 않는다.
5. 새 입력은 클라이언트에서 즉시 정리하고, DB 트리거도 같은 규칙을 적용한다.
6. 화면은 저장된 번호를 그대로 보여주며 한국어 접미사 `호`를 다시 붙이지 않는다.

## 이유

세대 목록 안에서는 `101`만으로도 호수임을 알 수 있고, 숫자 표기는 한국어·중국어 화면에서
동일하게 읽힌다. 좁은 두 패턴만 정리하면 표기를 통일하면서도 사용자가 이름처럼 적은 자료를
추측해 고치는 위험을 피할 수 있다.

중복 비교용 `normalizeUnitNumber`는 `0101`과 `101`, `b03`과 `B03`을 같은 세대로 판정한다.
저장·표시용 `canonicalUnitNumber`는 그 표기를 보존한다. 목적이 다르므로 두 함수를 합치거나
저장 과정에서 대문자화·앞자리 0 제거를 해서는 안 된다.

## 지켜야 할 계약

- `101호`, `101 호`, `B03호`, `b03 호`만 접미사를 제거한다.
- 운영에서 확인한 예외 60개는 글자 하나도 바뀌지 않는다.
- 사람이 적는 `return_visits.nickname`과 과거 요청·방문 기록의 스냅샷은 변경하지 않는다.
- 연결된 `return_visits.unit_number`는 세대 번호를 따라간다.
- 자동 표시명인 `return_visits.display_name`은 끝이 옛 세대 번호와 정확히 같을 때만 고친다.
- 번호 수정 결과가 같은 건물의 기존 세대와 겹치면 저장하지 않고 편집 화면과 입력을 유지한다.
- 일괄 추가는 기존 번호만 제외하고 나머지를 계속 추가한다.
- 이전 백업을 복원해도 DB 트리거가 같은 정규화를 적용한다. 정규화 충돌이 있으면 복원을
  조용히 진행하지 않고 UNIQUE 오류로 멈춘다.

## 포기한 대안

- 모든 `호`를 제거: 상호·설명·동 정보가 포함된 세대 이름을 훼손한다.
- 모든 세대에 `호`를 붙여 저장: 중국어 화면에도 한국어 접미사가 남고 자유 이름과 충돌한다.
- 비교용 정규화를 저장에도 사용: `B03`과 `0101`처럼 의미 있는 원문 표기를 잃는다.
- 클라이언트만 정리: CSV, 복원, RPC, 구버전 앱처럼 다른 쓰기 경로를 막지 못한다.

## 운영 상태

2026-09-06 최신 백업 뒤 운영 DB에 단일 트랜잭션으로 적용했다. 세대 수는 2,804개로
유지됐고 순수 `호` 표기 375개를 정리했다. 예외 60개는 그대로 남았으며 정규화 중복은
0건이다.

적용 전부터 `용성원룸 B동` 305·307의 정기방문 복제 칸에만 `호`가 남아 있어 최초 적용은
후검증에서 멈추고 전부 롤백됐다. 기존 연결 자료도 같은 보수적 규칙으로 동기화하도록
마이그레이션을 보완한 뒤 다시 적용했으며, 연결 불일치는 2건에서 0건이 됐다.
