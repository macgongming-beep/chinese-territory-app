## 0. 한 줄 요약

> "인도자 배정을 일정상세 안으로 넣는다. (1) 팀 짓기(사람) → (2) 구역 배분(지도/목록 토글) 두 화면. 모든 상태는 단일 draft에서 파생, 편집 중엔 localStorage, 마지막에 일정상세에서 '배정 공유' 한 번. 비공식/식당은 화면2 목록에서, 지도는 구역 전용."

## 1. 배경 / 현재 구조

### 1.1 현재 인도자 배정 (`MobileLeaderAssignment.tsx`, 1292줄)
- 별도 하단 탭 "배정" → 진입하면 오늘 일정 또 고름 (캘린더 중복)
- 3-step: 카드선택 → 팀구성 → 참가자 (step 전환 잦아 맥락 끊김)
- 모델: `team = { id, name, color, cardIds[], members[] }`,
  draft를 `localStorage(mobileLeaderAssignmentDraft:{eventId}:{user})`,
  공유상태 `draft/confirmed/shared`, 콜백은 이미 eventId 스코프
- 담당 카드 ~43개를 좁은 step1에 욱여넣음

### 1.2 일정상세 (`admin/AdminEventDetailSheet.tsx`, 697줄)
- 바텀시트. 신청자 전원 칩 strip, shared면 공유 배정 표시

### 1.3 지도 (`MapCanvas.tsx`)
- `cardBoundaries`(폴리곤), `onSelectCardBoundary(cardId)`(탭 핸들러),
  `selectedCardIds:Set`(색칠 강조), 폴리곤별 fillColor → "탭하면 팀색 칠"이 기존 인프라로 거의 됨

## 2. 도메인 제약 (확정)

1. 한 팀에 카드 여러 개 흔함 (구역2 / 구역+비공식) → 팀 개념 유지
2. 누구랑 누구 짝 = 인도자 수동 (자동분배 X)
3. 형식 비슷·인원 매번 다름 → "골격 복사"는 V2로 (사람은 매번 교체)
4. 하루 한 구만 감 (기흥구 OR 처인구) → 구 단위 범위 좁히기
5. 비공식·식당은 폴리곤 없음 → **지도 대상 아님, 목록에서만 배정**
6. 경계선 없는 구역카드는 인도자 배정 안 함 → 폴백 불필요
7. 관리자 카드 배정은 이번 범위 아님
8. **팀 인원 상한 없음** → 인원 수만 표시
9. **DB는 사용자별 cardIds만 저장** (`event_card_assignments` / `event_card_assignment_cards`). 팀의 teamId/이름/색/순서는 저장 안 됨 → 서버에서 draft 복원 시 팀 메타는 재생성(보존 안 됨)
10. **비공식/식당 배정은 기존 즉시 저장 방식 유지 (B안)** — draft에 안 넣음. localStorage draft는 **구역(cardIds) + 팀멤버만**

## 3. 새 설계

### 3.1 전체 흐름
```
일정상세 (AdminEventDetailSheet)
  └ [팀 구성 & 배정 →]   ← 인도자/관리자만, 보기전용 인도자는 비활성
       ↓ 풀스크린 진입
  화면1: 팀 짓기 (사람만)
       ↓ 팀 탭 (또는 화면2 sticky 팀바로 전환)
  화면2: 구역 배분 (지도/목록 토글, 활성팀 단위)
       · 즉시 반영, 저장 버튼 없음 (draft 자동저장)
       ↓ 뒤로
  일정상세
    └ [배정 공유] 한 번  ← draft → shared
```

### 3.2 화면1 — 팀 짓기 (사람 전용)
```
┌─ 傳道 13:00 배정 ─────────────────┐
│ 신청 9명                           │
│ [장웅][사용자1][사용자2][사용자3]  │ ← 탭 멀티선택
│ [사용자4][사용자5][엄민석]...      │
│  ✓ 2명 선택  [→ 새 팀으로 묶기]   │
│ ═══════════════════════════════   │
│ ┌──────────────────────────────┐ │
│ │ 팀 1   장웅·사용자1        [›]│ │ ← 탭 → 화면2(그 팀)
│ │ 🗂 구역 0 · 미배정           │ │
│ ├──────────────────────────────┤ │
│ │ 팀 2   사용자2·사용자3     [›]│ │
│ └──────────────────────────────┘ │
│ 미배정 👤 사용자4 사용자5          │ ← 탭 → 팀 선택 추가
│                      [공유 →]    │
└──────────────────────────────────┘
```
- 사람 멀티선택 → "묶기" → 팀 생성
- 미배정 사람은 기존 팀 멤버 영역 탭으로 추가
- **화면1은 순수 사람만** (비공식/식당 여기 없음 — 화면2로)

### 3.3 화면2 — 구역 배분 (핵심)

#### 헤더 = sticky (엑셀 행고정)
```
╔═══════════════════════════════════╗ ← sticky 시작
║ ‹  구역 배분            📍기흥구 ▾ ║
║ ┌──────────┐┌────────┐┌────────┐ ║ ← 팀바 가로스크롤
║ │● 팀1     ││ 팀2    ││ 팀3   →│ ║   탭=활성전환
║ │장웅·사용자1││사용자2 ││사용자5 │ ║
║ │🗂신갈동4외1││⚠구역없음││...    │ ║
║ └──────────┘└────────┘└────────┘ ║
║  [🗺️ 지도]  [☰ 목록]              ║
╚═══════════════════════════════════╝ ← sticky 끝 (스크롤해도 고정)
```
- 헤더는 앱 공통 패턴(‹ + 제목) 유지 → **일관성**
- 팀바 sticky → 색칠 중 스크롤해도 활성팀·배정현황 항상 보임
- 팀 칩 = `●활성 / 팀이름 / 구성원(인원수) / 구역요약`
- 구 선택 드롭다운 (기흥구/처인구/전체)

#### 지도 모드 (구역 전용)
```
[sticky 헤더]  ← 고정
┌──────────────────────────────┐
│   🗺️ 지도 (고정창, 핀치/드래그)│ ← page 스크롤 안 함
│   ┌────┐ 팀1 진한파랑+이름     │
│   └────┘  ┌────┐ 팀2 진한초록  │
│   ░░░ 미배정(회색점선)         │
└──────────────────────────────┘
│ ⓘ 비공식·식당은 목록에서       │ ← 안내 (지도는 구역만)
```
폴리곤 상태:
| 상태 | 채움 | 라벨 |
|---|---|---|
| 미배정 | 회색 20% + 점선 | 없음 |
| 활성팀 | 팀색 45% 실선 | 팀이름(흰글씨+그림자) |
| 다른팀 | 그 팀색 20% | 작게 |
| 줌 낮음 | 색만 | 라벨 숨김(확대 시) |

- 건물 핀 숨김 (배정은 구역 단위, 핀은 노이즈)
- 진입 시 선택 구 담당 카드에 자동 fit 줌
- 폴리곤 탭 = 활성팀 색칠 (토글). 다른팀 탭 = 활성팀으로 이동 + **"이동됨·실행취소" 토스트**

#### 목록 모드 (구역 + 비공식 + 식당)
```
[sticky 헤더]  ← 고정 (엑셀식)
┌──────────────────────────────┐
│ 🔍 검색      ☑ 미배정만        │
│ ▾ 기흥구·신갈동                │
│ │ ☑ 신갈동4  주택4  25%       │ ← 활성팀 배정(체크+강조)
│ │ □ 신갈동9  주택4  75%       │ ← 미배정
│ │ [팀2] 신갈동11 주택1        │ ← 다른팀(팀이름 pill), 탭→이동
│ ▾ 📁 비공식 카드               │
│ │ □ 비공식A  □ 비공식B        │
│ ▾ 🍴 식당                      │
│ │ □ 중화요리궁                │
└──────────────────────────────┘
```
- 행 = `체크 · 카드명 · 주택N/상가N · 진행률%`
- 다른팀 배정 = 팀이름 pill → 탭하면 활성팀으로 이동 (지도와 동일 규칙)
- 동별 그룹 (기존 step1 재활용), 비공식·식당도 같은 목록 하단 그룹
- page 자연 스크롤 + sticky 헤더 = 엑셀 행고정 동작

#### 모드별 스크롤
| 모드 | 스크롤 | 비공식/식당 |
|---|---|---|
| 목록 | page 자연 스크롤, 헤더 sticky | 같은 목록 하단 그룹 |
| 지도 | 지도 고정창(핀치/드래그) | 없음(목록에서만) + 안내 문구 |

### 3.4 일관성 원칙
- "이 카드 → 어느 팀"을 지도(색+이름)·목록(팀 pill) 동일 표현
- 둘 다 **단일 draft에서 파생**. 지도 전용/목록 전용 state 금지

### 3.5 배정 공유 + draft 관리 (가장 중요, v3 보강)

**draft 범위 (B안):**
- 단일 source of truth: **`draft.teams[]` = { teamId, name, color, order, cardIds[], members[] }**
- **구역 배정(cardIds) + 팀 멤버만 draft.** 지도·목록은 순수 파생
- **비공식/식당은 draft에 안 넣음** — 기존 즉시 저장 mutation 유지 (코덱스 B안). 화면2 목록에서 칩 탭 = 바로 Supabase 쓰기 (구역과 저장 타이밍 다름, 문서/UX에 명확히 분리)

**진입 시 draft 구성 (우선순위):**
1. localStorage draft 있고 서버보다 최신 → 그걸 이어서 (단 충돌 시 §아래 선택지)
2. 없거나 서버가 최신 → **서버 shared 배정에서 draft 재구성**
   - ⚠ **DB는 cardIds만 저장 → 팀 이름/색/순서는 보존 안 됨.** "같은 cardIds 가진 사람끼리 묶기"로 팀을 재생성하고 이름/색은 새로 부여 (원본과 100% 동일하지 않을 수 있음)

**참가자 sanitize (제미나이 — 필수):**
- draft 로드 시(로컬이든 서버든) **현재 `event.participants`와 교차 검증**
- 신청 취소·관리자 거절로 **현재 참가자에 없는 사람은 draft 팀 멤버에서 자동 제거**
- reducer 초기화 시점에 정제 단계 1개

**충돌 시 선택지 (코덱스 — 단순 경고 X):**
- local draft와 server shared가 둘 다 있고 어긋나면 → 조용히 덮지 말고 선택지:
  1. 서버 공유본 사용
  2. 내 임시 draft 이어서 편집
  3. 임시 draft 삭제
- (없으면 인도자가 짠 임시 팀이 조용히 날아감)

**공유 + 정리 (제미나이 — 실패 보호):**
- 일정상세 [배정 공유] → `onAssignCardsToEventParticipantsBulk(eventId, ..., {status:'shared'})`
- **API 성공(resolve) 직후에만 localStorage draft 정리** (네트워크 실패 시 draft 보존)
- eventId 관련 draft 키 정책: 관리자·인도자 둘 다 만질 수 있으므로 공유 후 **해당 eventId의 stale draft 처리 방침** 결정 필요 (V1: 본인 키만 정리 + 진입 시 sanitize로 방어)

## 5. 빌드 순서 (리스크 감소 시퀀싱)

> **목록 먼저 = 지도가 덜 중요해서가 아니라, 단일 draft reducer 아키텍처를 단순한 UI에서 먼저 못박기 위함.** 그게 단단하면 지도는 순수 파생 뷰로 끼우면 "그냥 동작". 지도는 1급 기능으로 유지.

| Phase | 작업 | 규모 |
|---|---|---|
| 1 | 일정상세 진입점 + 화면1 팀 짓기 + **단일 draft reducer** | 중 (2~3일) |
| 2 | 화면2 목록 뷰 + 비공식/식당 + 서버상태 진입로드 + 공유 | 중 (2일) |
| 3 | 화면2 지도 뷰 (색칠/이름라벨/구선택/자동줌/Undo토스트) | 중 (2~3일) |
| 4 | 권한 + QA, 기존 배정 탭은 **feature flag/병행 유지** (안정화 후 제거) | 소~중 (1~2일) |

**총 7~10일.** 데이터/백엔드 변경 없음.

## 6. 데이터 사용량 영향 (Supabase 최적화 영향 평가)

- **읽기: 조건부로 새 fetch 없음** — 진입 컴포넌트가 cards/buildings/cardBoundaries/calendarEvents/eventInformalAssignments/eventRestaurantAssignments를 **전역 store에서 props로 받는 전제**에서만 성립. 필요한 slice를 props로 못 받으면 fetch 추가됨 (코덱스 지적) → 진입점 설계 시 props 전달 확인 필수
- **쓰기: 구역 배정 공유 1회** → `refetchCalendar = fetchSlices(['calendar']) ≈ 14KB`
- **편집 중 구역(팀짓기/색칠/토글)은 localStorage** → Supabase 안 건드림
- ⚠ **단, 비공식/식당은 B안이라 칩 탭마다 즉시 Supabase 쓰기** (구역과 다름). 빈도 낮아 영향 작지만 "편집 중 0 write"는 구역에 한함
- **지도 타일 = 네이버 API** (Supabase egress 무관, 기존 지도 탭과 같은 쿼터)
- 결론: **구역 배정만 보면 영향 거의 없음.** 비공식/식당 즉시저장 + 진입 slice 누락 시엔 약간의 write/fetch 추가 가능

**구현 시 철칙:**
1. 토글·팀전환·구역색칠 시 **refetch 금지** (전부 클라이언트 state, draft 단일 reducer가 보장)
2. **폴리곤은 fillColor만 리렌더** (제미나이) — state 변경 시 폴리곤 컴포넌트 Unmount/Mount 금지, `React.memo`/참조 최적화로 색상 속성만 갱신. 수십~수백 폴리곤 색 즉각 변경 시 성능 좌우
3. 진입 컴포넌트는 필요한 slice를 props로 받을 것 (새 fetch 방지)

## 7-1. Undo (코덱스)
- 색칠/이동은 토스트뿐 아니라 **reducer에 "최근 작업 1회 되돌리기" action** 설계
- `lastAction` 보관 → 토스트의 [실행취소] 탭 시 reducer가 역연산
