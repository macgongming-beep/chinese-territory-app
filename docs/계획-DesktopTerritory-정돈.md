## 처음 생각한 방법을 버린 이유

"화면 덩어리를 컴포넌트로 뺀다" 가 자연스러워 보였다. 그래서 **떼면 몇 개를
넘겨야 하는지 세어 봤다:**

```
카드 관리 테이블   75개
Big Card          71개
구역선 모달 구간    56개
```

**props 70개짜리 컴포넌트는 지금보다 나쁘다.** 그리고 오늘만 해도
'값 하나가 파일 다섯을 거치다 한 곳을 빠뜨려 반쪽 커밋' 이 세 번 났다
(비공식 배정 두 번, 뒤로가기 한 번). 그 함정에 정면으로 걸어 들어가는 셈이다.

→ **화면을 떼기 전에 상태를 묶는다.** 묶고 나면 넘길 것이 대여섯 개가 된다.

## 단계

### A. 필터 21개 → `useTerritoryFilters` 훅  (제일 큰 덩어리)

- 상태 21개 + `filteredCards`(24줄, 조건 8개) + `filteredBuildings` + `pointRows` 판정
- **왜 먼저인가**: 가장 크고, 순수하고, `renderHook` 으로 시험할 수 있다.
  "왜 이 카드가 목록에 없지" 를 지금은 아무도 확인할 수 없다.
- **검증**: 필터 조합별 시험 + 변형 검사(조건 하나씩 빼서 그 시험만 깨지는지)
- **예상**: 컴포넌트 −250줄쯤

### B. CSV 6개 → `useCsvImport`,  병합 2개 → `useCardMerge`

- 각각 자기 상태 + 핸들러가 한 묶음이다 (`parseCsvFile`, `handleImportCsv`,
  `handleApplyCardMerge`, `handleUndoCardMerge`)
- **검증**: renderHook + 이미 있는 `parseBuildingCsv` 시험 재사용
- **예상**: −150줄쯤

### C. 그다음에야 화면을 뗀다

A·B 뒤에는 테이블에 넘길 것이 `filters` / `selection` / `data` / `handlers`
네 묶음쯤이 된다. 그때 **카드 관리 테이블(691줄)** 부터 뺀다.

- **검증**: `@testing-library/react` 로 실제 렌더 — 행이 그려지는지,
  정렬 머리를 누르면 순서가 바뀌는지, 체크가 되는지
- **여기서 멈춰도 된다.** Big Card·모달까지 안 해도 파일이 절반이 된다.

## 하지 않을 것

- **한 번에 다 하기.** 단계마다 커밋하고, 각 단계에서 앱이 도는지 본다.
- **동작 바꾸기.** 정돈이 목적이다. 이상한 걸 발견하면 적어만 두고 따로 고친다.
- **Context 도입.** props 를 줄이려고 context 를 쓰면 데이터 흐름이 숨는다.
  묶음 객체로 충분하다.

## 위험

| | |
|---|---|
| 훅으로 빼면서 렌더 타이밍이 달라진다 | `useMemo` 의존성을 그대로 옮긴다. 빠뜨리면 값이 안 바뀐다 |
| 시험이 통과해도 무는 게 아니다 | 오늘 네 번 겪었다. **단계마다 변형 검사** |
| 화면 추출은 시험이 어렵다 | 그래서 C 를 마지막에 둔다. A·B 는 순수해서 쉽다 |
| 중간에 멈추면 어중간해진다 | 단계마다 그 자체로 완결되게 한다 |

## 안 하는 선택지도 있다

로직은 이미 꽤 뺐고 파일이 도는 데 문제는 없다. **더 급한 것은
anon 쓰기 권한 축소**다 (다른 회중 배포 전 필수). 이 정돈은 그다음이어도 된다.

물어볼 것: **A → B 까지만 하고 멈추는 게 나은가, C 까지 가는 게 나은가?**
