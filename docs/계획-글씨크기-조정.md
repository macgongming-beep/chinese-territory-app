# 글씨 크기 조정 — 방법 고르기

2026-08-28. "너무 작아서 안 보인다" 는 분들이 있다. 리뷰받고 시작하려고 쓴다.

## 실측한 현재 상태

```
글씨 크기를 정하는 곳        2,515 곳
  App.css / index.css        1,543  (전부 px. rem·em·clamp 0)
  컴포넌트 인라인 스타일        972  (fontSize: 14 같은 숫자)
  그중 계산식이라 기계 변환이 못 잡는 것      8   ← 0.3%

line-height                  배수 219 · px 3      ← ✅ 글씨를 키우면 줄 간격도 따라 커진다
고정 height                  CSS 708 · 인라인 156  ← ⚠ 여기가 위험하다
position: fixed              CSS 25 · 인라인 47
100vh/svh/dvh                17
canvas 에 글자 그리기          없음                 ← ✅ 전부 DOM 이라 CSS 로 덮인다
```

**⚠ 핀치 확대가 꺼져 있다.** `index.html` 의 viewport 에
`maximum-scale=1.0, user-scalable=no`. **지금 사용자에겐 키울 방법이 아예 없다.**

## 방법 A — 핀치 확대를 허용한다 (한 줄)

viewport 에서 `maximum-scale=1.0, user-scalable=no` 를 뺀다.

- **얻는 것**: 오늘 밤에 배포된다. 사용자가 원하는 만큼, 원하는 화면에서만 키운다
- **잃는 것 ⚠ (이게 크다)**: iOS 는 **입력칸 글씨가 16px 미만이면 눌렀을 때 화면을
  저절로 확대**한다. 그리고 **스스로 돌아오지 않는다.**
  이 앱은 15px 이하 글씨가 **1,247곳**이다 — 검색창·메모칸을 누를 때마다
  화면이 확대된 채 남는다. 지금 없는 짜증을 새로 만든다
- 지도 화면에서 핀치가 지도 확대와 겹칠 수 있다 (네이버 지도가 제스처를 먹으면
  괜찮지만 확인이 필요하다)

## 방법 B — 설정에 '글씨 크기' (보통 / 크게 / 아주 크게)

`--fs` 라는 배수를 하나 두고, 모든 글씨 크기를 그 배수로 곱한다.

```css
:root { --fs: 1 }
.tbl-cell { font-size: calc(14px * var(--fs)) }
```
```tsx
<span style={{ fontSize: 'calc(14px * var(--fs))' }}>
```

- **바꾸는 방법**: 정규식 기계 변환. `font-size: 14px` → `font-size: calc(14px * var(--fs, 1))`,
  인라인 `fontSize: 14` → `fontSize: 'calc(14px * var(--fs, 1))'`.
  **2,515곳 중 2,507곳(99.7%)이 기계로 잡힌다.** 나머지 8곳은 손으로.
  rem 으로 바꾸는 것보다 낫다 — 나누기(14/16)를 안 해도 되고, 인라인 스타일에도 그대로 쓴다
- **저장**: 사용자별로 (`chsFontScale:<userId>` — 언어와 같은 방식).
  기기마다 다르게 둘 수 있는 게 오히려 맞다 (폰은 크게, PC 는 보통)
- **얻는 것**: 필요한 사람만 키운다. 레이아웃이 다시 배치돼 잘리지 않는다.
  iOS 자동확대 문제가 없다
- **잃는 것 ⚠**: **고정 height 가 864곳**이다. 글씨가 커지면 그 안에서 넘치거나
  잘린다. 특히 버튼·칩·탭·표 머리.
  → 배수를 **1.15 / 1.3 정도로 묶고**, 주요 화면을 실제로 보면서 맞춰야 한다.
  "다 키우고 끝" 이 아니라 **넘치는 곳을 찾아 고치는 일이 본론**이다

## 방법 C — 뿌리에 `zoom` 을 준다 (`#root { zoom: 1.2 }`)

한 줄이고 글씨·간격·높이가 **같이** 커져서 안 잘린다.

- **잃는 것 ⚠**: `position: fixed` 가 **72곳**, `100vh` 류가 **17곳**이다.
  zoom 안에서 fixed 는 기준이 달라지고 vh 는 배수가 안 맞는다.
  하단탭·모달·토스트·지도 오버레이가 어긋날 가능성이 크다. 확인 비용이 B 보다 클 수 있다

## 무엇을 권하는가

**B.** 이유:

- A 는 한 줄이지만 **iOS 에서 새 문제를 만든다** (15px 이하 1,247곳).
  이건 "안 보인다" 를 "누를 때마다 화면이 확대돼서 짜증난다" 로 바꾸는 거래다
- C 는 싸 보이지만 fixed 72곳이 걸린다. 깨지면 어디가 깨졌는지 찾기 어렵다
- B 는 **기계 변환이 99.7% 를 덮고**, line-height 가 배수라 줄 간격이 따라오고,
  canvas 글자가 없어 전부 CSS 로 덮인다. 조건이 좋다

**단, B 의 진짜 일은 변환이 아니라 '넘치는 곳 고치기' 다.** 864곳의 고정 높이 중
글씨를 담는 곳을 찾아 `min-height` 로 바꾸거나 `height` 를 빼야 한다.
그래서 **1.15 부터 시작해 화면을 보며 넓히는 것**을 권한다.

## 단계

```
1. --fs 도입 + 기계 변환 (CSS 1,543 · 인라인 964) + 손으로 8곳
   → 이 시점에 --fs=1 이라 **화면이 하나도 안 바뀌어야 한다.** 그게 검증이다
2. 설정에 '글씨 크기' 셋 (보통/크게/아주 크게 = 1 / 1.15 / 1.3)
   사용자별 저장, 언어와 같은 자리
3. 1.3 으로 놓고 주요 화면을 돌며 넘치는 곳을 고친다
   (하단탭 · 구역 표 · 카드 칩 · 캘린더 · 모달 버튼)
4. 시험: --fs 를 바꿨을 때 실제로 계산값이 바뀌는지 (jsdom 은 calc 를 안 풀어서
   getComputedStyle 로는 확인이 안 될 수 있다 — 어떻게 물게 할지 정해야 한다)
```

## 묻고 싶은 것

1. **B 가 맞나?** A 를 함께 하는 선택지도 있다 (핀치는 지도에서만 유용할 수 있다)
2. **`calc(14px * var(--fs, 1))` 방식의 함정이 있나?** 특히 `font: ` 축약형,
   미디어쿼리 안의 font-size, 상속(부모가 이미 calc 인데 자식이 em 을 쓰는 경우)
3. **4번 시험을 어떻게 물게 하나?** jsdom 이 calc 를 안 푸는데, "변환을 되돌려도
   통과하는 시험" 이 되면 안 된다. 브라우저에서 확인하는 수밖에 없나?
4. 고정 높이 864곳을 **미리 다 고칠지**, 아니면 **1.3 에서 실제로 깨지는 것만**
   고칠지. 후자면 못 본 화면이 남는다
