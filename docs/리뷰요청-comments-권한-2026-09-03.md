# 리뷰 요청 — comments 역할별 권한

이 문서는 적용 전 리뷰와 반영 기록이다. 1차 리뷰의 GO 조건을 반영한 뒤
2026-09-03 운영에 적용했다.

## 운영 읽기 감사

2026-09-03, 운영 DB를 변경하지 않고 확인했다.

```text
댓글                         88행
author_id NULL                0행
author_id와 현재 이름 불일치    0행
soft deleted                 15행
부모가 없는 댓글               12행
  calendar_event             8행 / 사라진 일정 4개 / soft deleted 3행
  notice                     4행 / 사라진 공지 1개 / 전부 soft deleted

현재 정책                     4개
TEMP 쓰기 정책                 3개
Realtime publication          없음
```

부모 없는 12행은 권한 변경과 별개다. polymorphic target이라 FK가 없고 부모 삭제 때
정리되지 않은 기존 데이터다. 이번 마이그레이션에서 임의로 지우지 않는다.

## 적용하려는 계약

- SELECT: 공개 범위 유지. 헤더 없는 Realtime도 실제 이벤트로 검증
- INSERT: 세션의 `author_id`와 현재 `app_users.name`이 모두 일치해야 함
- UPDATE: 작성자는 내용 수정·soft delete. admin/developer는 남의 댓글을 soft delete만
  할 수 있고, 자기 댓글은 작성자와 동일하게 수정 가능
- 작성자 삭제: 기존 UI처럼 `deleted_at`을 바꾸는 soft delete
- 영구 DELETE: admin/developer만
- `target_type`, `target_id`, `author_id`, `author_name`: 생성 뒤 변경 금지
  - 관리자 API도 변경 불가
  - postgres 소유 security definer인 `rename_user_name_references`만 통과
- 계정 삭제로 `author_id=NULL`이 된 댓글: 공개 읽기 유지, 관리자만 수정·삭제

구현은 `20260903_1000_owner_comments.sql`이다. 식별 칸은 RLS만으로 칸별 변경을
막을 수 없어 invoker trigger로 보호한다. RLS는 행 소유권을 맡는다.

## 테스트 DB 결과

`npm run smoke:comments` 21/21 통과:

- 무세션 INSERT 거부
- 다른 사용자의 id 또는 이름으로 INSERT 거부
- 본인 INSERT·내용 수정·soft delete 허용
- 타인 내용 수정과 본인 영구 DELETE 거부
- target 두 칸과 author 두 칸 변경 거부
- 이름 변경 RPC는 기존 댓글 이름을 정상 변경
- 사용자 삭제 뒤 댓글이 `author_id=NULL`로 남음
- 일반 사용자는 고아 댓글 수정 거부, 관리자는 soft delete 허용
- 공개 SELECT 유지
- 헤더 없는 WebSocket에서 실제 INSERT 이벤트 수신

변형 다섯 가지를 각각 넣었고 모두 해당 smoke가 실패했다. 매번 정상 마이그레이션을
재적용했고 마지막 정상 smoke도 통과했다.

1. INSERT 정책 `with check(true)`
2. UPDATE 정책 `using(true) with check(true)`
3. 식별 칸 보호 trigger 제거
4. DELETE 정책 `using(true)`
5. Realtime publication에서 comments 제거
6. 관리자 UPDATE 제한을 이전 식별 칸 전용 trigger로 되돌림

추가 검증: 626 tests, lint 오류 0(기존 DesktopMap 경고 1), build, 재잠금/긴급복구
시뮬레이션 통과.

## 적용 중 발견한 기존 버그

`CommentSection`은 Realtime을 구독하지만 `comments`가 `supabase_realtime`
publication에 들어간 적이 없었다. 기존부터 다른 사용자의 댓글이 실시간으로
갱신되지 않았다. 마이그레이션에서 idempotent하게 publication에 추가한다.

## 반박받고 싶은 것

1. 작성자 이름을 INSERT 정책의 `app_users` 서브쿼리로 대조하는 것이 RLS 평가나
   성능 면에서 문제인가?
2. admin/developer의 남의 댓글 UPDATE를 `deleted_at` 한 칸으로 제한한 trigger가
   현재 UI 계약과 일치하는가?
3. 작성자의 영구 DELETE를 막고 soft delete만 허용한 것이 기존 호출 경로를 깨뜨리나?
4. `current_user`가 postgres 계열이면 식별 칸 변경을 허용한 trigger에 다른 definer
   우회가 있는가? 현재 확인한 의도된 경로는 이름 변경 RPC다.
5. 부모 없는 댓글 12행은 별도 정리로 두는 게 맞나? 향후 부모 삭제 trigger와 보존 중
   어느 계약이 자연스러운가?
6. 테스트 DB 결과로 운영 적용 전 관문이 충분한가?

## 1차 리뷰 반영

- 관리자가 남의 댓글 내용을 바꿀 수 있던 범위를 닫았다. 작성자 본인은 역할이 A여도
  편집할 수 있고, 남의 댓글은 `deleted_at` 외의 칸이 하나라도 바뀌면 거부한다.
- INSERT 정책이 `app_users.name` SELECT에 의존하는 사실을 권한표의 계정 행에 적었다.
  향후 app_users 읽기 축소 전에 이 결합을 먼저 처리해야 한다.
- 보호 트리거가 postgres 계열 definer를 통과시키는 예외를 감사 도구에 추가했다.
  `app_users`·`visit_histories`·`comments`를 쓰는 definer 함수가 새로 생기면 목록에 뜬다.
  테스트 DB에서 실제 7개 함수가 출력돼 헛도는 검사가 아님을 확인했다.
- 관리자 UPDATE 제한을 옛 trigger로 되돌리자 정확히 관리자 본문 변조 항목만 실패했다.
