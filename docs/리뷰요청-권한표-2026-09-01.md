## 권한표를 만들다 발견한 P1 두 건

운영은 긴급 개방 0, 열린 쓰기 정책 0으로 재잠금됐다고 판단했지만 검사가
**RLS가 켜진 표의 정책만** 봤다. 아래 두 표는 RLS가 꺼진 채 anon DML grant가 있었다.

1. `special_periods`: 비로그인 요청도 특별기간을 생성·수정·삭제 가능
2. `login_logs`: 비로그인 요청도 로그인 기록을 생성·수정·삭제 가능

준비한 수정:

- `20260901_0900_guard_special_periods.sql`
  - 읽기는 모두 유지
  - 쓰기는 `request_is_admin()`만
- `20260901_0910_guard_login_logs.sql`
  - 직접 쓰기 grant 회수 + RLS 켬
  - 기록은 기존 auth definer, 조회는 `get_login_logs` RPC만
- `status:security`에 **RLS-off + anon 쓰기 grant 표 목록** 추가
- 재잠금 preflight/최종 검증에도 같은 검사를 추가
- TEMP가 아닌 쓰기 정책은 이름이 아니라 실제 조건식에
  `request_session_user_id` 또는 `request_is_admin` 관문이 있는지 검사

테스트 DB API smoke:

```text
special_periods
  관리자 생성·수정·삭제       OK
  무세션 읽기                 OK
  무세션 생성                 401
  일반 사용자 생성            401

login_logs
  무세션 직접 INSERT          401
  관리자 직접 INSERT          401
  auth_login 기록             OK
  본인 get_login_logs         OK
  일반 사용자의 남의 기록 조회 401
```

변이 검사도 했다.

- `special_periods` INSERT 정책을 `with check(true)`로 바꾸자 두 검사가 HTTP 201로 실패
- `login_logs` RLS를 끄고 grant를 복구하자 두 검사가 HTTP 201로 실패
- 마이그레이션 재적용 뒤 둘 다 다시 전체 통과
- 재잠금 전체 리허설에서 RLS-off `login_logs` 변이를 심자 적용이 거부되고 전체 롤백
- `with check(true)`인 비-TEMP 쓰기 정책도 최종 검증이 거부

**운영 적용 상태 (2026-09-01):** `login_logs`는 단독 적용 완료. 320행 유지,
RLS ON, anon/authenticated 직접 DML 회수, PostgREST 무세션 직접 접근 401,
인증 기록 함수와 `get_login_logs`는 롤백 smoke 통과. `special_periods`도 별도 적용해
공개 읽기와 관리자 CRUD는 유지하고 무세션·일반 사용자 쓰기는 401임을 운영 API로 확인했다.
전체 RLS-off + anon 쓰기 표는 0개다.

## 권한표에서 특히 반박받을 것

1. `special_periods`를 관리자·개발자 전용으로 본 것이 맞나?
2. `login_logs` 직접 접근을 모두 막아도 놓친 앱/cron 경로가 있나?
3. U가 건물·세대를 어디까지 구조적으로 편집할 수 있어야 하나?
4. L의 범위는 자기 카드인가, 자기가 인도하는 일정인가, 둘 다인가?
5. 정기방문·재방문의 소유자는 등록자/지정 방문자/카드 인도자 중 누구인가?
6. `review_tasks`는 죽은 기능으로 보고 쓰기를 막아도 되나?
7. 이름 문자열 기반 소유권으로 RLS를 만들기 전에 user id 전환이 필요한가?

## 구현 순서 제안

1. P1 두 표 운영 적용 완료
2. `chat_room_mutes` 본인 행만으로 배포 도구 파일럿 (운영 0행이라 업무 검증은 아님)
3. `comments`를 첫 실사용 파일럿으로. 새 글은 세션 `author_id`를 강제하고,
   탈퇴로 `author_id`가 NULL인 글은 읽기 유지·관리자만 수정
4. 관리자 전용 단순 표
5. 일정 묶음은 RPC 중심
6. cards/buildings/units/visits는 업무 결정 후 마지막

모든 매트릭스에 SELECT와 Realtime 실제 이벤트 수신을 포함한다.

추가 확인 결과 `special_periods` 설정 라우트는 코드에서도 admin/developer만 접근한다.
운영 0행이라 기능 존폐는 따로 정하되, P1 관리자 쓰기 차단은 현재 UI 계약과 일치한다.

`comments.author_id`는 nullable일 뿐 아니라 FK가 `ON DELETE SET NULL`이다. 따라서
단순 NOT NULL 전환은 계정 삭제 계약을 함께 바꾸므로 이번 파일럿의 선행 조건으로 두지 않는다.

추가 지적: `assign_cards_bulk_tx`가 없을 때 세 배정 표에 직접 쓰는 클라이언트
레거시 폴백이 남아 있다. 새 회중 설치가 마이그레이션을 요구하는 지금은 제거하는 편이
맞다고 보는데 반박해 달라.
