# 리뷰 요청 — 역할별 권한 1차 운영 적용

권한표 리뷰 뒤 실제 운영에 세 단계를 적용했다. 다음은 운영 데이터 67행이 있는
`comments`이므로, 그 전에 지금까지의 적용·검증에서 놓친 것을 찾고 싶다.
동의보다 반박을 원한다.

## 운영 적용 결과

| 대상 | 전 | 후 | 운영 검증 |
|---|---|---|---|
| `login_logs` | RLS OFF + anon DML | RLS ON, anon/authenticated 직접 DML 회수 | 320행 유지. 무세션 직접 접근 401. 자동 로그인 기록 + `get_login_logs` 롤백 smoke |
| `special_periods` | RLS OFF + anon DML | 공개 SELECT + A만 I/U/D | 무세션/U 생성 401. A 생성·수정·삭제 성공. 임시 행 0 |
| `chat_room_mutes` | 로그인 사용자면 남의 행도 I/U/D | 본인 `user_id`만 I/U/D, 공개 SELECT 유지 | 본인 I/U/D 성공, 무세션·타인 조작 차단. 임시 행 0 |

현재 운영 상태:

```text
긴급 개방             0
쓰기 관문             89 (TEMP 83 + 최종 6)
SELECT 공개 정책      27
RLS-off anon 쓰기 표   0
```

## 검증한 것

- 세 마이그레이션 모두 테스트 DB와 운영에서 별도 단일 트랜잭션 적용
- 전용 API smoke:
  - `smoke:login-logs`
  - `smoke:special-periods`
  - `smoke:chat-room-mutes`
- `chat_room_mutes`는 INSERT 관문을 `true`로 바꾸자 무세션·타인 행이 실제 생성됨
- DELETE 관문을 `true`로 바꾸자 타인 행이 실제 삭제됨
- 정상 정책 재적용 뒤 전체 smoke 재통과
- 재잠금 → 긴급복구 → 재잠금 리허설 통과
- RLS-off 표와 이름만 그럴듯한 가짜 정책 변형은 재잠금/최종 검증이 거부하고 롤백
- 전체 테스트 626개, lint 오류 0 (기존 `DesktopMap.tsx` 경고 1개)

## 함께 바꾼 검증 도구

역할별 최종 정책으로 바꾸면 `TEMP_session_gate_*` 개수가 줄어든다. 기존 재잠금은
TEMP 이름만 관문으로 인정해서 정상 정책을 오히려 거부했다. 이제 이름 대신
`USING/WITH CHECK`에 `request_session_user_id` 또는 `request_is_admin`이 있는
쓰기 정책을 센다. 상태 출력은 TEMP와 최종 정책을 나눠 보여 준다.

⚠ 정적 검사는 **helper 이름의 존재만** 본다. `helper() OR true`처럼 의미상 열린
조건을 증명할 수 없다. SQL 주석에도 정적 안전망일 뿐이고 실제 차단 증명은 API
smoke가 맡는다고 적었다. 이 분리가 충분한지 반박해 달라.

## 다음 `comments`에 제안한 계약

현재 67행, 19명이 사용했고 모든 기존 행의 `author_id`는 채워져 있다. 그러나 컬럼은
nullable이고 FK가 `app_users(id) ON DELETE SET NULL`이다.

- SELECT: 현재 공개 범위 유지 + Realtime 실제 이벤트 확인
- INSERT: `author_id = request_session_user_id()` 강제
- UPDATE(편집·soft delete): 본인 또는 A
- `author_id IS NULL`: 읽기는 유지, 수정은 A만 (탈퇴 뒤 fail-closed)
- `author_id NOT NULL`은 이번 선행 조건으로 두지 않는다. 그러면 계정 삭제/FK 계약까지
  함께 바꿔야 하기 때문이다.

## 반박받고 싶은 것

1. `login_logs`에서 table grant까지 회수한 것이 auth definer·cron·관리 화면에 남긴
   숨은 회귀가 있는가?
2. `special_periods`의 `to public` 공개 SELECT와 A 쓰기 정책 사이에 permissive OR
   우회가 남아 있는가?
3. `chat_room_mutes`를 모두 공개 SELECT로 유지한 것이 개인정보 노출인가? 앱·알림
   트리거 호환 때문에 유지했지만, 본인 SELECT로 좁히면 Realtime/트리거가 깨지는가?
4. 정적 관문 검사 + 표별 API 변형 smoke의 분업이 충분한가? 검증기가 더 강제해야 할
   최소 조건이 있는가?
5. `baseline.sql` 뒤 `migrations/*.sql` 이름순 실행으로 새 회중 재현이 되는가?
   이번 세 파일의 순서·의존성에 빠진 것이 있는가?
6. 다음 `comments` 계약이 맞나? 특히 관리자에게 모든 댓글 수정·soft delete를 허용할지,
   탈퇴 사용자의 NULL 댓글을 관리자만 수정하게 할지.
7. `comments` 운영 적용 전에 추가해야 할 매트릭스·복구 절차가 있는가?

운영 DB에는 현재 세 단계가 이미 적용돼 있다. 리뷰 중 문제를 찾으면 새 마이그레이션으로
고치고, 이미 적용한 파일을 과거 수정처럼 취급하지 않는다.
