# 배포 후 로딩 멈춤 수정

## 원인과 범위

기준 `136834b`. 사용자가 보고한 iPhone 증상 자체를 기기에서 재현한 것은 아니다.
코드에서 확인된 문제는 즉시 skipWaiting, activate의 모든 창 navigate,
플러그인 autoUpdate의 별도 reload, 제어권 인계 전에 실행되는 applyUpdate의 reload다.
fetchAll은 거절되면 loading을 내리지 못했고, 정상 반환된 오류는 끝에서 지웠다.

## 변경

- prompt 모드. 배포 시 새 SW는 waiting. 기존 문서와 precache 유지.
- 최상위 skipWaiting과 activate navigate, 시작 후 20초 자동 적용 제거.
- 명시적인 업데이트 버튼에서 SKIP_WAITING. 새 controller 확인 후 창당 reload 1회.
- clientsClaim 유지. 다른 열린 창도 native controllerchange로 같은 버전에 맞춤.
  따라서 업데이트 안내에는 다른 창도 갱신된다고 알린다.
- 12초 뒤 로딩 화면에 수동 복구 버튼. 45초 데이터 로딩 기한.
- 초기 로딩 실패는 오류 화면, 기존 화면의 백그라운드 실패는 토스트.
- 복구 시 로그인 저장소, Cache Storage 전체, SW 등록을 삭제하지 않음.
- ko/zh/en 문구 제공.

## 확인

- 실제 useStore 훅: 조회 reject, 오류 응답, 무응답, 성공 후 백그라운드 실패.
- 실제 AppLoading: 지연 중 자동 reload 없음, 버튼 호출, 실패 후 재시도, 번역.
- controller 인계 전에는 적용 완료로 처리하지 않음. 인계 timeout 뒤 재시도 가능.
- 변형: controller 검사 제거 시 시험 실패. loading 해제 제거 시 3개 시험 실패.
- `scripts/smokePwaUpdate.mjs`: 실제 pwa.ts/sw.ts/업데이트 UI를 빌드한 두 버전.
  두 창의 입력을 보존한 채 B 배포, A의 lazy 파일을 서버에서 제거해도 캐시에서 읽힘.
  오프라인에서도 A 파일 조회 성공. 수동 업데이트 후 두 창 B 전환, 클릭한 창 reload 1회.
  localStorage 로그인 sentinel 유지. 모바일 390px에서 로딩 복구 버튼·가로 넘침 확인.

브라우저 시험 실행: Playwright가 설치된 환경에서
`node scripts/smokePwaUpdate.mjs`. 다른 위치에 설치돼 있으면
`PLAYWRIGHT_MODULE`에 해당 `playwright/index.mjs`의 절대 경로를 지정한다.
합성 화면으로 시험하므로 운영 API나 자료를 쓰지 않는다.

## 적용 시 유의

- 옛 autoUpdate 문서는 waiting 안내를 처리하지 못하므로 이번 첫 전환은 모든 앱 창을
  닫고 다시 여는 과정이 한 번 필요할 수 있다. 새 코드만으로 옛 문서의 코드를 고칠 수 없다.
- iPhone standalone 실기기 전환은 사용자 확인이 남아 있다.
- 45초 기한은 UI 대기 제한이며 진행 중인 모든 네트워크 요청을 취소하는 것은 아니다.
  초기 실패 후 복구는 문서를 다시 여는 방식이다.
- SW 대기는 DB 스키마 호환성을 해결하지 않는다. 파괴적 스키마 변경은 별도 전환 필요.
- 스키마나 운영 설정 변경은 없다. 기존 운영 점검 공지는 별도 설정으로 유지된다.
