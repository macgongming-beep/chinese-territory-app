# baseline 뒤에 이어서 실행할 것

`supabase/baseline.sql` 은 **뽑은 시점의 사진**이다. 그 뒤에 운영에 넣은 것은
여기 적고, 새 프로젝트를 세울 때 **순서대로** 이어서 실행한다.

> ⚠ 이 목록을 안 적으면 새 회중은 **그 기능이 없는 채로** 시작한다.
> 실제로 그럴 뻔했다 — 중복 병합 RPC 를 운영에 넣고 baseline 을 안 갱신했다.
> `applied/` 는 "다시 실행하지 않는 기록" 이라 설치 절차가 건드리지 않는다.

## 실행 순서

| 날짜 | 파일 | 무엇 |
|---|---|---|
| 2026-08-25 | `applied/v3_merge_duplicate_buildings_tx.sql` | 중복 병합 트랜잭션 RPC + 호수/주소 정규화 함수 |
| 2026-08-25 | `v3_merge_conflict_fix.sql` | 위 RPC 고침 — 흡수될 건물끼리의 호수 충돌을 놓치고 있었다 |

## baseline 을 다시 뽑으면

이 목록을 **비운다.** 다시 뽑은 baseline 에 이미 들어 있기 때문이다.
다시 뽑는 법은 `docs/새-회중-설치.md` 의 ③ 을 볼 것.

## 왜 이 방식인가

지금 규모(회중 1~5곳)에서는 migration 도구를 들이는 것보다 이 목록 하나가 낫다.
다만 **DB 를 바꿀 때마다 여기 한 줄 적는 것을 잊으면** 그 순간 낡는다.
줄이 서너 개 넘게 쌓이면 baseline 을 다시 뽑아 비우는 편이 낫다.
